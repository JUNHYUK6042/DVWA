# API Security

## 개요

- API(Application Programming Interface)는 서버와 클라이언트가 데이터를 주고받는 인터페이스입니다.
- 웹 서비스에서 API는 URL 엔드포인트를 통해 특정 리소스를 반환하며,  
  인증 및 권한 검증이 미흡하거나 구버전 엔드포인트가 방치될 경우 인가되지 않은 접근과 민감 정보 노출로 이어질 수 있습니다.

---

## API(Application Programming Interface)

- 서버가 외부 요청에 데이터를 반환하는 인터페이스입니다.
- 웹에서는 주로 URL 경로에 리소스를 명시하는 REST 방식이 사용됩니다.

```
GET /api/v1/user/1
→ {"id": 1, "name": "user1", "email": "user1@example.com"}
```

- 클라이언트는 URL 구조만 파악하면 서버에 직접 요청을 보낼 수 있습니다.
- 서버 사이드에서 권한 검증이 없으면 누구든 임의의 데이터에 접근할 수 있습니다.

---

## API 버전 관리 (API Versioning)

- 동일한 기능을 `/v1/`, `/v2/`처럼 버전으로 구분하여 운영하는 방식입니다.

```
/api/v1/user/1   ← 구버전 (보안 설계 미흡)
/api/v2/user/1   ← 신버전 (보안 패치 적용)
```

- 신버전에서 취약점을 패치해도 구버전 엔드포인트가 살아 있으면 공격자가 구버전으로 우회 접근할 수 있습니다.
- 사용하지 않는 구버전 API는 반드시 폐기하거나 접근 차단 처리해야 합니다.

---

## BOLA (Broken Object Level Authorization)

- API 요청 시 리소스 ID(숫자, 일련번호 등)를 변조하여 타 사용자의 데이터에 접근하는 취약점입니다.
- OWASP API Security Top 10의 1순위 항목입니다.

```
/api/v1/user/1  → 사용자 A 데이터 반환
/api/v1/user/2  → 사용자 B 데이터 반환  ← 타 사용자 접근
/api/v1/user/3  → 사용자 C 데이터 반환  ← 권한 검증 없이 가능
```

- 서버가 요청 ID와 로그인 사용자 ID가 일치하는지 확인하지 않을 때 발생합니다.
- ID가 숫자처럼 예측 가능한 구조이면 1, 2, 3... 순서로 전체 사용자 데이터를 수집할 수 있습니다.

---

## 과도한 데이터 노출 (Excessive Data Exposure)

- API 응답에 클라이언트가 필요로 하지 않는 민감한 필드까지 포함하여 반환하는 취약점입니다.

```json
// 과도한 노출 — 불필요한 민감 필드 포함
{"id": 1, "name": "user1", "role": "admin", "password": "해시값", "ssn": "주민번호"}

// 정상 응답 — 필요한 필드만 반환
{"id": 1, "name": "user1"}
```

- 화면에 표시되지 않아도 응답 자체에 민감 정보가 포함되면 노출된 것입니다.
- 개발 편의를 위해 DB 조회 결과를 그대로 반환할 때 자주 발생합니다.

---

## SHA-256 해시와 크랙

- SHA-256은 단방향 해시 알고리즘으로, 원문에서 해시값은 계산할 수 있지만 역산은 불가능합니다.
- 단, 연산 속도가 빠르기 때문에 레인보우 테이블이나 무차별 대입 방식의 크랙에 취약합니다.

```
평문: password123
SHA-256: ef92b778bafe771e89245b89ecbc08a44a4e166c06659911881f383d4473e94f
```

- 레인보우 테이블은 미리 계산된 해시 값 데이터베이스로, 해시만 있으면 빠르게 원문을 찾을 수 있습니다.
- 솔트(Salt)가 없는 단순 SHA-256 해시는 동일한 입력이 항상 동일한 해시를 생성하므로 취약합니다.
- bcrypt, argon2 등 느린 해시 알고리즘을 사용하면 크랙에 필요한 시간을 현저히 높일 수 있습니다.

---

## 공격 흐름

```
1. 클라이언트 소스코드 또는 Network 탭에서 API 엔드포인트 패턴 파악
        ↓
2. 신버전(v2) 확인 → 구버전(v1) 존재 추론 후 접근 시도
        ↓
3. v1 엔드포인트에서 민감 정보(password 해시 등) 노출 확인
        ↓
4. ID 값을 순차 변조하여 전체 사용자 데이터 수집 (BOLA)
        ↓
5. 수집한 해시를 크랙 도구로 원문 패스워드 획득
```

---

## 특징

- API 취약점은 화면에 보이지 않아도 Network 탭이나 소스코드만 분석하면 공격 경로를 파악할 수 있습니다.
- BOLA는 특별한 기술 없이 URL의 ID 값만 바꿔도 공격이 가능합니다.
- 구버전 API 미폐기와 과도한 데이터 노출이 결합되면 단일 취약점보다 훨씬 큰 피해로 이어집니다.

---

## 대응 방안

- API 요청 시 세션과 요청 ID를 비교하여 본인 데이터만 조회할 수 있도록 서버 사이드 권한 검증 구현
- 사용하지 않는 구버전 API 엔드포인트 폐기 또는 라우팅 차단
- API 응답에서 불필요한 민감 필드 제거, 클라이언트에 필요한 데이터만 반환
- SHA-256 대신 bcrypt, argon2 등 느린 해시 알고리즘 적용
- 소스코드에 API 엔드포인트 경로가 노출되지 않도록 설계
