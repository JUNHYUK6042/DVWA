# CSRF

## 개요

- CSRF는 인증된 사용자의 세션을 이용하여 사용자가 의도하지 않은 요청을 서버에 전송하는 공격 방식입니다.
- 서버는 정상 사용자의 요청과 공격자가 유도한 요청을 구별하지 못합니다.
- 별도의 취약점 없이도, 로그인 상태만으로 공격이 성립합니다.

---

## 핵심 개념

- 사용자가 로그인된 상태를 악용하여 공격이 수행됩니다.
- 브라우저는 요청 시 쿠키(세션)를 자동으로 포함하여 전송합니다.
- 사용자의 권한으로 공격자가 원하는 요청이 실행됩니다.
- GET / POST 방식 모두 공격이 가능합니다.

---

## 공격 방식

공격자는 악성 페이지를 만들어 사용자가 해당 페이지에 접속하도록 유도합니다.  
사용자가 로그인된 상태라면, 브라우저가 자동으로 인증 정보(쿠키 등)를 포함하여 요청을 전송합니다.  
이로 인해 사용자의 의도와 상관없이 비밀번호 변경, 게시글 작성, 송금 등의 기능이 수행됩니다.

---

## 예시

### GET 방식 — 비밀번호 변경 공격

```html
<!-- 공격자가 만든 악성 페이지에 삽입 -->
<img src="http://target.com/change_pw?pw=hacker123" style="display:none">
<!-- 피해자가 페이지에 접속하는 순간 비밀번호 변경 요청이 자동 전송됨 -->
```

- 이미지 태그의 src 속성으로 요청이 자동 발생합니다.
- 피해자는 화면에 아무것도 보이지 않아도 요청이 이미 전송된 상태입니다.

---

### POST 방식 — 송금 요청 공격

```html
<!-- 자동 제출 폼 방식 -->
<form id="csrf_form" action="http://bank.com/transfer" method="POST">
  <input type="hidden" name="amount" value="1000000">
  <input type="hidden" name="to" value="attacker_account">
</form>
<script>document.getElementById('csrf_form').submit();</script>
<!-- 페이지 로드 즉시 폼이 자동 제출되어 이체 요청이 전송됨 -->
```

- 피해자가 악성 페이지를 열면 자동으로 폼이 제출됩니다.
- 피해자는 자신의 계좌에서 공격자 계좌로 이체가 발생하는 사실을 인식하지 못합니다.

---

## 특징

- 사용자의 인증 상태를 그대로 이용합니다.
- 별도의 취약점 없이도 발생할 수 있습니다.
- GET / POST 요청 모두 공격이 가능합니다.
- XSS와 달리 스크립트 실행이 불필요하며, 단순 요청 전송만으로 공격이 성립합니다.

---

## 대응 방안

- CSRF 토큰 적용 — 요청마다 고유 토큰 발급 및 검증
- Referer 또는 Origin 헤더 검증 — 요청 출처 확인
- SameSite Cookie 설정 — 외부 사이트에서 쿠키 전송 차단
- 중요 요청 시 추가 인증 요구 — 재로그인, OTP 등
